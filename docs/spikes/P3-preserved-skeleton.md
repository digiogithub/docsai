# Spike P3 — the preserved skeleton

**Risk mitigated**: P2 from `technical-analysis-presentations.md` §7 — *«PowerPoint offers to
repair the file»* — and the design it depends on, the package-level raw block of §5.1.

**Question**: can a writer read a `.pptx`, carry every part it does not understand as opaque
bytes, rebuild only the slides from a model, and produce a package the applications still open?

**Date**: August 2026 · **Measured over**: `corpus/pptx` (twelve fixtures after this increment
added `charts-embedded` and `smartart-fallback`), the same twelve re-emitted by LibreOffice
Impress 24.2.7.2 as a *foreign producer*, and one 20 MiB deck built to price the memory · **Oracle**:
LibreOffice 24.2.7.2 headless, `--convert-to pdf`, text compared with `pdftotext`.

**Decision**: **the preserved skeleton works and is the write strategy for Phase 14.** Over 24
decks, 24 rewrites and 24 mutating rewrites — 48 packages — **not one part was lost, added or
reordered, and every one converted**. The package boundary is safe.

The finding that matters is the other one, and it is a warning rather than a comfort: **the
skeleton protects the package, not the slide.** On decks written by a foreign producer the
harness silently dropped every run property inside the slides it rebuilt — 14 typefaces and 14
sizes in one fixture, down to zero — and neither the part list, the diff, nor LibreOffice noticed.
An intact skeleton around a flattened slide still renders a different deck.

**Risk P2 stays open**, and deliberately: the acceptance criterion names PowerPoint, PowerPoint is
not on this machine, and LibreOffice was measured here to be *too lenient to stand in for it* —
see §2.4, where a package with five dangling relationships opened without a word.

---

## 1. Method

A harness outside the tree, in Rust on `zip` 2 and `quick-xml` 0.37 — the workspace's own
versions, and nothing else, so that what the spike proves the workspace can already build. Three
modes, run over every fixture:

1. **`rewrite`** — the thing under test. Read every ZIP member into `(name, bytes, compression
   method, timestamp)`. Find the slide parts *through `[Content_Types].xml`*, never by file name:
   `slide-order.pptx` exists because names lie. Parse each slide into a small model, write it back
   **from that model**, and re-emit the package with every other member untouched, in the original
   order.
2. **`naive`** — the control. The same package minus every part a slide-only reader does not
   understand, with the content types and relationships that pointed at them left exactly as they
   were. This is the mistake the spike prices.
3. **`diff`** — part lists, member order, per-part bytes, compression method and timestamp.

### 1.1 What the model carries, and why it is small on purpose

A byte copy of a slide would prove nothing, so the slide is genuinely rebuilt:

| Element | Treatment |
|---|---|
| `p:sp` with a `p:txBody` | **Modelled**: id, name, `p:ph`, paragraphs and their text |
| `p:spPr`, `a:bodyPr`, `a:pPr` | **Carried verbatim** — geometry, autofit and bullets are attributes of the model, not parsed |
| `a:rPr`, `a:endParaRPr` | **Dropped** — the harness models text, not character formatting |
| `p:pic`, `p:graphicFrame`, `p:cxnSp`, `mc:AlternateContent`, any `p:sp` without a `p:txBody` | **Raw**: the exact incoming bytes, spliced back in. The raw-block idea, one level below the package |
| Everything outside `p:spTree` | Head and tail bytes, verbatim |

That split is not an accident of the harness: it is the DocMark boundary — what the profile writes
as Markdown, versus what spike P2 signed off as a raw block — moved into the writer.

### 1.2 Foreign producers

Twelve fixtures generated by `corpus/generate.py` share the conventions the harness re-emits, so a
byte-identical round trip over them proves less than it looks. LibreOffice Impress was used as a
second, unrelated producer: `--convert-to pptx` over the corpus gives twelve decks written by
somebody else's serialiser, with different element order, different attribute spelling and
direct formatting the corpus does not use.

### 1.3 The oracle, and its limits

LibreOffice headless converts each deck to PDF; the text is extracted and compared with the same
deck's baseline. It answers *«does it still open, and does it still say the same thing»*. It does
**not** answer *«would PowerPoint repair it»*, and §2.4 shows the gap is wide.

## 2. Results

### 2.1 The round trip is exact at the package boundary

| Corpus | Decks | Parts lost | Parts added | Order preserved | Non-slide parts changed |
|---|---|---|---|---|---|
| `corpus/pptx` | 12 | 0 | 0 | 12/12 | 0 |
| LibreOffice-produced | 12 | 0 | 0 | 12/12 | 0 |
| 20 MiB deck with a stored `.mp4` | 1 | 0 | 0 | yes | 0 |

Compression method and timestamp survive per member — the 20 MiB media part goes back in
`stored`, not re-deflated. All 12 corpus decks round trip **byte-identically, slides included**;
that is a property of the corpus sharing the harness's conventions, not a claim about foreign
input, and §2.3 is where the honest number is.

The output package is 25 bytes larger than its input on the 20 MiB deck. Every part is identical;
the container around them is rebuilt, and ZIP metadata is not part of the contract.

### 2.2 Everything still opens, including after an edit

`rewrite --mutate` makes the edit an agent would make — retitle the deck, append a bullet — so
that the write path cannot be a byte copy in disguise:

| Run | Decks | Converted by LibreOffice | Retitle visible in the PDF | Added line visible |
|---|---|---|---|---|
| corpus, rewritten | 12 | 12 | — | — |
| corpus, mutated | 12 | 12 | 12/12 | 7/12 |
| foreign, rewritten | 12 | 12 | — | — |
| foreign, mutated | 12 | 12 | 12/12 | 7/12 |

The added line lands on 7 of 12 because five fixtures have no second text placeholder to append to
— their body is a table, a picture, a chart, a diagram or free shapes. That is the fixture, not
the harness.

Rendered text is identical to the baseline on 12/12 corpus decks and 11/12 foreign ones. The one
difference is §2.3.

### 2.3 What the slide rebuild loses on a foreign producer

Only the slide parts differ, on all twelve foreign decks — the boundary holds. Inside them:

| Fixture | Slide bytes | Paragraphs | Text identical | `a:latin` | `sz=` | `a:endParaRPr` |
|---|---|---|---|---|---|---|
| `basic-slides` | 3612 → 2645 | 3 → 3 | yes | 3 → 0 | 3 → 0 | 3 → 0 |
| `bullets-levels` | 6400 → 4153 | 7 → 7 | yes | 14 → 0 | 14 → 0 | 7 → 0 |
| `shapes-geometry` | 4049 → 3146 | 2 → 2 | yes | 2 → 0 | 2 → 0 | 2 → 0 |

Structure and text survive; **typography does not**. `bullets-levels` is the fixture whose
rendering changed, and it changed for exactly this reason: with `Calibri Light` and `sz="4400"`
gone the glyph metrics differ, and the extracted text loses two blank lines and the space in
`1. Uno`. Nothing structural moved — the paragraph count is 7 before and after.

This is the docx lesson from spike R1 restated one level down. There, the question was what a
library drops between reading and writing a part. Here the parts are safe and the question is what
*our own model* drops inside one.

### 2.4 The control: dropping what you do not understand fails silently

`naive` removes the parts a slide-only reader has no use for and leaves the pointers to them:

| Fixture | Parts dropped | LibreOffice | Rendered text |
|---|---|---|---|
| `charts-embedded` | 3 — `chart1.xml`, its rels, the embedded workbook | opens, no complaint | **12 values gone**, slide is a bare title |
| `smartart-fallback` | 5 — four `dgm:` parts and the `dsp:` drawing | opens, no complaint | *unchanged* |
| the other ten | 0 | opens | unchanged |

Two things are worth writing down.

**The damage is silent.** No dialog, no warning, no error code — a chart simply stops existing.
A user who converts a deck and does not scroll to slide 4 never learns.

**LibreOffice cannot see the SmartArt loss at all**, because it never draws the diagram: it renders
the `mc:Fallback` shape, which is a slide element and was never at risk. Five parts vanished, the
package now has five dangling relationships, and the oracle reports success. An OPC-conformant
consumer is entitled to refuse that package, and PowerPoint is the one that does.

That is the whole argument for keeping the PowerPoint criterion open rather than declaring it
green by proxy.

### 2.5 Cost

| Measurement | Value |
|---|---|
| 12 decks (85 KB total) rewritten | 0.06 s, peak RSS 3.6 MiB |
| One 20 MiB deck | 0.03 s, peak RSS **56 MiB** |
| Damaged inputs: 5361 truncations and byte flips over three fixtures | 0 panics — 5027 `Err`, 334 parsed (damage in bytes the harness carries opaquely) |

Time is free. Memory is not: holding every part costs roughly **2.7× the package size**, because
the source buffer and the part copies coexist. A 200 MB deck with video would want 500 MB, which
is not acceptable and is not inherent — a part that is never inspected can be streamed from the
source archive to the target one without ever being fully resident. The harness does not, because
the harness is a spike.

Zero panics over damaged input is the `AGENTS.md` §6 bar, met by construction: opaque parts are
never parsed, so most corruption cannot reach a parser at all.

## 3. Analysis

### 3.1 Where the proof lives

The plan left this open — *«a throwaway script proves nothing that survives, and a crate is Phase
13 work»* — and the answer measurement gives is: **neither, and the boundary is the deliverable**.

What survives this spike is not code. It is the split in §1.1: which elements a writer may rebuild
and which it must carry. That table is portable to Phase 14 whether the code is or not, and it is
what would have been lost had this been a script.

The harness is 500 lines, uses two dependencies the workspace already has, and is discarded, as
R1's and P1's probes were. Phase 14 rebuilds it inside `docsai-office` against the real model.

### 3.2 The skeleton is necessary and not sufficient

The two measurements bracket the design:

- Without it (§2.4), a writer destroys parts it never looked at, silently.
- With it (§2.3), the writer destroys formatting *inside* the parts it did look at, also silently.

So the skeleton retires one class of loss and leaves the other exactly where it was. The rule that
falls out is narrower than «preserve the package»:

> **A writer may only rebuild an element whose every child it can either model or carry. Anything
> else is raw.**

`a:rPr` is the first thing that rule bites on: Phase 14 either models run properties or keeps them
verbatim. It may not do what this harness did.

### 3.3 Why discovery through content types is not a detail

The harness finds slides through `[Content_Types].xml`, and the reason is one line in the results
that does not stand out: `slide-order.pptx` round-trips correctly. A writer that globbed
`ppt/slides/slide*.xml` would have got the same answer here by luck. One that assumed
`slide1.xml` is the first slide would already be wrong on this corpus.

### 3.4 What LibreOffice is good for

It is a real consumer, it is scriptable, and it caught nothing. That is not a criticism — it is
the calibration. LibreOffice answers *«is this deck still readable»*, which is worth having;
`--convert-to pptx` was the more valuable half of it, because it produced twelve decks our own
generator could not have written and those are what §2.3 found the run-property loss on.

## 4. Decision

**Adopted for Phase 14.**

1. **Every part is opaque unless the writer has a reason to touch it.** Read `(name, bytes,
   compression method, timestamp)`, write them back in the incoming order. Not «preserve the parts
   we know about» — preserve everything, and treat rebuilding as the exception.
2. **Slide parts are found through `[Content_Types].xml`**, never by file name or by position.
3. **Inside a rebuilt part, the §1.1 split is normative**: model it, carry it verbatim, or leave
   the whole element raw. An element whose children are only partly understood is raw.
4. **`a:rPr` and `a:endParaRPr` are on the carry-or-model side**, decided by name because this
   spike proved what happens when they are on neither.
5. **Parts a deck reaches but the writer never inspects are streamed**, not buffered, once the
   package exceeds a size worth caring about. §2.5 gives the multiplier that makes this a real
   requirement rather than a preference.

### Accepted, with the reason written down

- **The output package is not byte-identical to the input even when every part is.** ZIP metadata
  is rebuilt. Nothing in the format depends on it, and the alternative — copying central directory
  entries verbatim — buys a property nobody has asked for.
- **Timestamps are preserved per member**, which means a deck that came in with 2026-01-01
  everywhere goes out that way. This is deliberate: a diff between two round trips must be about
  content.

## 5. Status of the risks

- **P2** (PowerPoint offers to repair) — **not closed, and the LibreOffice half is not evidence
  that it is close.** 48 packages convert; §2.4 shows the oracle also accepts a package with five
  dangling relationships. What P3 does establish is that the *skeleton mechanism* introduces no
  loss at the package boundary, so if PowerPoint repairs a deck, the cause is inside a rebuilt
  part and §1.1 says where to look. Reproduction steps for anyone with PowerPoint are in §6.2.
- **P3** (freeform / SmartArt / animations fragment the effort) — **reduced**. SmartArt cost the
  writer nothing: five parts and an `mc:AlternateContent`, all raw, all intact. The fragmentation
  risk is a reader-side and DocMark-side problem, which is where P2 (the spike) left it too.
- **P5** (autofit stale) — untouched, but note that `a:bodyPr` is carried verbatim here, so a
  round trip **preserves a stale `fontScale`** rather than fixing it. That is the correct default
  and the warning Phase 13 owes the user is still owed.

### Still not verified

- **PowerPoint.** The criterion the plan wrote is open, by environment, not by choice.
- **Animations, transitions, embedded OLE and video** as *slide* content. The 20 MiB `.mp4` in
  §2.5 was a package part, not a `p:pic` with a media relationship, and no fixture carries
  `p:timing`. A deck whose slide XML references parts by `r:id` will exercise a path this spike
  did not: the raw shape is preserved, but nothing checked that its relationship still resolves.
- **A slide the writer must delete.** Everything here rewrote slides in place. Removing one means
  editing `p:sldIdLst`, the presentation relationships and the content types — three parts the
  skeleton currently declares opaque. Phase 14 has to open that hole deliberately.
- **Real-world decks.** `AGENTS.md` §6 rules them out of the corpus, and the LibreOffice-produced
  twelve are the closest available stand-in for a foreign producer.

## 6. Reproducing this spike

### 6.1 The harness

Outside the tree, discarded like R1's and P1's probes:

```bash
python3 corpus/generate.py
cargo new /tmp/p3-harness && cd /tmp/p3-harness
cargo add anyhow@1 quick-xml@0.37
cargo add zip@2 --no-default-features --features deflate
```

Three modes over a package read as `Vec<(name, bytes, method, timestamp)>`:

- `rewrite [--mutate] <in> <out>` — slide parts from the `[Content_Types].xml` overrides whose
  type is `…presentationml.slide+xml`; each parsed into the §1.1 model with `quick-xml`, capturing
  unmodelled elements as byte spans via `Reader::buffer_position()`; written back and re-emitted
  in the original member order. `--mutate` appends ` (revisado)` to the first title placeholder
  and a paragraph to the next placeholder.
- `naive <in> <out>` — keep `[Content_Types].xml`, `_rels/`, `docProps/`, `ppt/presentation.xml`,
  `ppt/slides/`, `ppt/slideLayouts/`, `ppt/slideMasters/`, `ppt/notesSlides/`, `ppt/notesMasters/`,
  `ppt/theme/`, `ppt/media/`; drop the rest and change nothing else.
- `diff <a> <b>` — part sets, member order, per-part bytes, compression method, timestamp.

### 6.2 The oracle

LibreOffice is installed here but its launcher does not resolve its own libraries; call the binary
with the path set, or every run fails with `libreglo.so: cannot open shared object file`:

```bash
export LD_LIBRARY_PATH=/usr/lib/libreoffice/program HOME=/tmp/p3/home
soffice_bin=/usr/lib/libreoffice/program/soffice.bin
$soffice_bin --headless --norestore -env:UserInstallation=file:///tmp/p3/profile \
    --convert-to pdf --outdir /tmp/p3/base corpus/pptx/*.pptx
# the foreign producer:
$soffice_bin --headless --norestore -env:UserInstallation=file:///tmp/p3/profile \
    --convert-to pptx --outdir /tmp/p3/foreign corpus/pptx/*.pptx
pdftotext -q a.pdf - | diff - <(pdftotext -q b.pdf -)
```

**The open criterion, for whoever has PowerPoint.** Ten minutes:

1. `cargo run -- rewrite corpus/pptx/charts-embedded.pptx out.pptx`, then the same for
   `smartart-fallback.pptx` and `notes-speaker.pptx`.
2. Open each in PowerPoint. The criterion is that **no repair dialog appears** and that the chart
   is still a chart — right-click → *Edit Data* must open the embedded workbook.
3. Repeat with `--mutate` and confirm the retitled slide saves again from PowerPoint without
   complaint. A deck PowerPoint opens but refuses to re-save is a failure too.
4. Run `naive` on `charts-embedded.pptx` and open that. It is expected to fail, and confirming it
   *does* is what proves PowerPoint is a stricter oracle than LibreOffice — §2.4 measured that
   LibreOffice accepts it.

Record the outcome in this section and, if step 2 passes on three decks, close risk P2 in
`docs/technical-analysis-presentations.md` §7.

### 6.3 The corpus fixtures this spike added

`charts-embedded.pptx` and `smartart-fallback.pptx` were listed in the 12-A table and built here,
because a skeleton spike with nothing in the package the writer fails to understand tests nothing.
Both are in `corpus/generate.py` and reproducible with `python3 corpus/generate.py --check`.
