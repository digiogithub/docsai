# 30 — Phase 12 A: the pptx corpus, built by hand

Increment 12-A of [[29-phase-12-plan]], the first work of the presentations track after Phase 11
closed in [[28-phase-11-mcp]]. It runs before the three spikes because all three consume decks.

## What it does

Ten `.pptx` fixtures under `corpus/pptx/`, generated by `corpus/generate.py` like every other
fixture in the corpus, one trait per file. There is **no reader yet** — Phase 13 builds it — so
there are no goldens and no Rust test touches these files. The only gate is
`generate.py --check`, which now covers `pptx/` too.

| Fixture | Trait it isolates |
|---|---|
| `basic-slides.pptx` | Title + body placeholders, two slides. The floor of the format |
| `slide-order.pptx` | `p:sldIdLst` deliberately disagreeing with the `slideN.xml` names |
| `placeholders-cascade.pptx` | Placeholders stating nothing — everything from layout and master |
| `placeholders-empty.pptx` | Empty placeholders and an empty paragraph between two full ones |
| `bullets-levels.pptx` | `a:pPr@lvl` nesting, `buChar` from the master, `buAutoNum` overridden |
| `notes-speaker.pptx` | `ppt/notesSlides/*` plus the notes master they require |
| `notes-crossed.pptx` | Notes parts numbered against the slides (added in 13-F, [[40-phase-13-notes]]) |
| `reading-order.pptx` | A `p:spTree` that is not the reading order (added in 13-G, [[41-phase-13-reading-order]]) |
| `raw-preserved.pptx` | A group, a `custGeom`, `p:transition` and `p:timing` (added in 13-I, [[43-phase-13-raw]]) |
| `tables-simple.pptx` | `p:graphicFrame` → `a:tbl` |
| `images-anchored.pptx` | DrawingML `p:pic` with explicit `a:xfrm` |
| `shapes-geometry.pptx` | `prstGeom` free shapes and a `p:cxnSp` connector |
| `autofit-stale.pptx` | `a:normAutofit@fontScale` computed for text that no longer fits |

Two fixtures from the plan's list are **not** here yet: `charts-embedded.pptx` (needs an embedded
xlsx workbook part) and `smartart-fallback.pptx` (needs a `dgm:*` subtree plus its
`mc:AlternateContent` fallback drawing). Both are substantially larger than the ten above and
neither is needed until P1 measures fidelity; they are the first thing to add when it does.

## Files and symbols touched

- `corpus/generate.py` — new "PPTX corpus" section: `build_pptx`, `slide`, `title_body_slide`,
  `notes_slide`, `sp_tree`, `shape`, `ph`, `a_p`, `tx_body`, `xfrm`, plus the `THEME`,
  `SLIDE_MASTER`, `SLIDE_LAYOUT` and `NOTES_MASTER` constants and the ten `pptx_*` generators.
- `corpus/generate.py` — two new shared helpers in the package-plumbing section, `rels_part` and
  `content_types`. The docx and xlsx builders still inline their own copies; unifying them is a
  refactor this increment deliberately did not take on.
- `corpus/generate.py` — `digest_tree` now walks `pptx/`.
- `corpus/opc_check.py` — new structural checker (see below).

## Why it looks like this

**Built by hand, not with `python-pptx`.** The plan named that library; the generator's own
module docstring names the opposite rule, and `generate.py --check` runs on three CI platforms
where no pip install has happened. The full argument is in [[29-phase-12-plan]]. The consequence
worth repeating: every byte of these fixtures is visible as source in the generator, so a future
failing golden points at a line a human wrote.

**The package carries a real cascade.** A master with `p:txStyles`, a layout that inherits from
it, and slides whose placeholders state nothing. A corpus that flattened the cascade — geometry
and fonts spelled out on every shape — would open in PowerPoint and answer none of Phase 12's
questions, because the placeholder cascade *is* the hard part of pptx.

**The theme is complete on purpose.** Twelve scheme colours, both font slots, three entries in
each of the four format lists. An incomplete theme is one of the common ways a generated package
earns a repair dialog, which is the exact failure risk P2 is about.

## A defect found and fixed inside this increment

The first version of `a_p` took a `ppr` string and spliced it into the `a:pPr` start tag, which
emitted **two** `a:pPr` elements in one paragraph for the `buAutoNum` case. Well-formed XML,
invalid against the schema, and `corpus/opc_check.py` did not catch it — because it is a
structural checker, not a schema validator. `bullet` is now child content of the single `a:pPr`
the paragraph is allowed. Recorded because it is exactly the class of error the missing schema
gate (analysis §5.5) exists to catch, and this increment could not run that gate.

## How it was verified

- `python3 corpus/generate.py` then `--check`: reproducible, 87 files (77 before).
- `corpus/opc_check.py` green on all ten fixtures. It checks the four things that actually break
  a generated package: XML that does not parse, a part with no content type, a relationship
  whose target is not in the zip, and an `r:id`/`r:embed` used by a part but not declared in its
  `.rels`. Proved non-vacuous two ways: green on the existing 23 docx/xlsx packages, and red on
  a control built by deleting one `Relationship` element.
- `cargo test --workspace`, `cargo fmt --all -- --check`: green, and no suite picked up the new
  corpus — correct, since nothing reads pptx yet.

## What is NOT verified, and it matters

**No fixture has been opened by PowerPoint or LibreOffice.** LibreOffice is installed on this
machine but broken (`soffice.bin: error while loading shared libraries: libreglo.so`), and
PowerPoint is not available at all. `opc_check.py` proves the packages are structurally coherent;
it does **not** prove Office opens them without a repair dialog, and the double-`a:pPr` defect
above is proof that the gap between those two statements is real.

So: these ten fixtures are structurally sound and reproducible, and their acceptance as *valid
decks* is open. Closing it is the first task of 12-D (spike P3), which needs a working Office
anyway. Until then, treat the corpus as provisional — a fixture that turns out to need a repair
dialog is a fixture to fix, not a finding about the reader.
