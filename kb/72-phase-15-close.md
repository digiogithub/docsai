# 72 — Phase 15 K: the P2 gate prepared, and the phase closed with one box open

Increment **15-K** of [[61-phase-15-plan]], on top of [[71-phase-15-render]]. The last one, and the
only one in the phase whose deliverable is **not a piece of software**: *the PowerPoint checklist of
`docs/spikes/P3-preserved-skeleton.md` §6.2, run by a human on three decks and recorded with its
outcome; risk P2 closed if it passes; docs, CHANGELOG, README, `AGENTS.md` status and the acceptance
criteria checked here.*

## The one thing this increment could not do

**The checklist has not been run.** PowerPoint is not on this machine, LibreOffice on it is broken
(`soffice.bin: libreglo.so`), and no agent is a human sitting in front of an application. Closing
risk P2 on the strength of two green CI gates would be exactly the failure `AGENTS.md` §7 rule 3 is
written against — one level worse than a false warning, because a risk marked closed stops being
looked at.

So **P2 stays open**, and what 15-K delivers is everything *around* the human step, prepared so the
owner can run it in one sitting:

1. **Three decks and a negative control**, built and checked.
2. **The form**: `docs/spikes/P2-powerpoint-gate.md`, item by item, with what counts as a pass and
   what counts as a failure stated before the first tick.
3. **`docs/technical-analysis-presentations.md` §7.1**: the state of the evidence in writing — what
   the gates prove, what they cannot reach — plus the exact table row that replaces the P2 row when
   the form is signed, so closing it is one edit and no fresh judgement.
4. **The acceptance criteria settled** in [[61-phase-15-plan]] and in `docs/development-plan-v2.md`.
5. **The phase close**: CHANGELOG, README, `AGENTS.md` §1, and this record.

## The three decks, and why these three

Not committed. They are derived byte for byte from the tracked corpus and the tracked writer, so
committing them would add an artefact class the repository does not carry (the only binaries here
are `corpus/`, generated by `corpus/generate.py` and checked by `--check`) and would freeze a file
whose whole point is to be rebuilt from the writer *as it is today*. They are built into
`target/p2-gate/` — gitignored, beside the CLI that wrote them — by the paste in §1 of the form.
Building them in `target/` also keeps `corpus/` clean: `default_assets_dir_for` writes the skeleton
asset beside the *source* file, so converting in place would litter the corpus with an `assets/`
tree.

Phase 15 has exactly three paths that produce bytes, and there is one deck for each:

| Deck | Source | Path | Why only PowerPoint can answer it |
|---|---|---|---|
| **A** `A-charts-edited.pptx` | `charts-embedded.pptx`, title retyped | preserved package spliced (15-A/B/F) | whether an archive of original stored bytes with **one** rebuilt slide part is still a package PowerPoint trusts; and *Edit Data* on the chart is a live check that a copied part survived the splice |
| **B** `B-smartart-edited.pptx` | `smartart-fallback.pptx`, title retyped | raw re-injection (15-D) | LibreOffice takes the `mc:Fallback` text box; only PowerPoint resolves `mc:Choice` and draws the five `dgm:` parts. P3 §2.4 lost four of those five to a naive rewrite **with no visible change at all** |
| **C** `C-plain-template.pptx` | four slides of attribute-free Markdown, no skeleton | whole package generated on the embedded template (15-G) | **no application has ever opened this file.** Every other path re-emits bytes a real producer wrote; this is the only package docsai authors end to end |

`D-raw-edited.pptx` (from `raw-preserved.pptx`: a group, a custom geometry, `p:transition`,
`p:timing`) is offered as an optional fourth — those are the raw families deck B does not carry, and
no corpus deck combines them with SmartArt. `N-negative-control.pptx` is **not** a docsai output: it
is `charts-embedded.pptx` with the chart part, its rels and the embedded workbook removed and the
relationships left dangling, which is P3 §6.2 step 4 and the reason a page of green ticks means
anything — P3 §2.4 measured LibreOffice opening that very shape of package in silence.

**Not covered by any deck**: a slide-level OLE embedding (`p:oleObj`). The corpus has no such
fixture; deck A's embedded workbook is reached as a `package` relationship behind a chart, which is
not the same thing. Said here rather than implied away.

Checked with `corpus/opc_check.py`: `ok` for A, B, C and D; **`FAIL`** for N, naming
`rIdChart -> ../charts/chart1.xml … not in package`. The control on the control works.

## What the form asks, and what decides it

Seven items. **The repair dialog is item 1**, alone, before anything else is looked at, because it
is the failure mode the whole phase was designed against and every item below it assumes the file
opened. Then: the edit landed and only the edit (2); the chart is still a chart and *Edit Data*
opens its workbook (3); the SmartArt is a diagram and not its fallback text box, the group is still
a group, the transition still plays (4); the generated deck has four slides on sensible layouts with
its text in real placeholders, checked in Outline view (5); each deck **re-saves** from PowerPoint
and reopens clean (6) — a deck PowerPoint opens but will not save is a failure too; and the files
PowerPoint re-saved come back through `docsai roundtrip` (7), which is the cheapest real
foreign-producer test this project will ever get and is free while the files are in hand.

The pass/fail rules are written before the table: a repair dialog in any wording is a failure even
if the repaired deck looks perfect; a missing object is a failure; a font substitution is *not* — it
is an observation, and the render gate owns that question with a measured threshold. And the whole
run is void if **N opens clean**, because then PowerPoint is not the strict oracle this project
assumed and every other tick is worth less.

## A defect found while assembling the decks — recorded, not fixed

The first attempt at deck A did what P3 §6.2's `--mutate` did: retyped the title **and** appended a
paragraph. The paragraph became a *third shape* on a slide the package gives two, and the writer
took the whole slide back to the bytes it was read as — losing the title edit with it. It is not
silent (`[Minor] degraded slide 1: the model holds 3 shape(s) and the slide 2; adding or removing a
shape is not this increment's, so the whole slide was copied unchanged`), and it is honest about
what it did. But the warning says «not this increment's» and there is no longer an increment: 15-G
seeds a *slide* the model added, not a *shape* added to a preserved slide, and the failure is
all-or-nothing at slide granularity — one unrepresentable addition discards every good edit on that
slide.

Not fixed here, and deliberately: a phase close that quietly changes the writer invalidates every
measurement the phase just made (§7 rule 1). Deck A retypes the title only. The defect is carried
forward below.

## What Phase 15 delivered, and how each part was proven

Eleven increments, [[62-phase-15-package]] to this one. The deck now goes out as a `.pptx`:

- **15-A** the preserved package re-emitted entry by entry — member order, compression method and
  stored bytes copied, not inflated and re-deflated.
- **15-B** the slide from the model, one text body at a time; everything around it stays the bytes
  that were read.
- **15-C** pictures, tables and media, with `_rels` and `[Content_Types].xml` *spliced* rather than
  rewritten.
- **15-D** raw re-injection at the original z-order; a foreign dialect dropped with a warning.
- **15-E** notes pages, and `p:sldIdLst`/`p14:sectionLst` restated when the model's slides are not
  the package's.
- **15-F** the stale autofit scale dropped when — and only when — the text actually changed.
- **15-G** the deck with no skeleton, on a template embedded in the binary and generated from source
  by `corpus/generate.py`.
- **15-H** `roundtrip` for decks and the per-category fidelity metric; the whole corpus idempotent,
  after the measurement found two silent writer defects.
- **15-I** CI gate 1: the vendored ECMA-376 XSDs over every part the writer changed or created.
- **15-J** CI gate 2: the render diff, with a threshold measured rather than guessed.

## What Phase 15 carries forward

Collected here so the next phase finds them in one place instead of in eleven increments' prose.

1. **The human P2 gate itself.** `docs/spikes/P2-powerpoint-gate.md`, unrun. Owner action, not a
   code action. Closes the phase's third acceptance criterion and risk P2.
2. **Gate 2 has never rendered.** `corpus/render_gate.py` is green on its comparator and on a
   stand-in renderer only. The first real numbers come from the first CI run, and **the threshold of
   2.5 may have to move when they do** ([[71-phase-15-render]]).
3. **LibreOffice is broken on the development machine.** `libreoffice-core` owns
   `/usr/lib/libreoffice/program/soffice.bin`, `libreglo.so` is missing and only ~120 `.so` files are
   in that directory; a reinstall of `libreoffice-core` would most likely fix it. It blocks gate 2
   locally and the LibreOffice half of the P2 checklist. Environment action for the owner.
4. **`<a:p/>` does not survive a round trip** ([[70-phase-15-xsd]]). The writer normalises it to
   `<a:p><a:endParaRPr/></a:p>`: schema-valid, visually identical, **not byte-identical**, which
   quietly dents 15-A's byte-identity claim for any deck in the wild that spells it short. No corpus
   deck does, so nothing here hides it and nothing here catches it either. Fixing it means the IR
   recording which spelling the source used — a `docsai-model` change.
5. **A preserved table whose grid the model moved is copied with a warning** ([[64-phase-15-media]],
   [[68-phase-15-template]]). The `a:tbl` writer exists only for slides the writer *generates*.
   Nothing owns writing a moved grid back into a preserved slide, and it needs row heights and
   `a:tcPr` in `docsai-model` first.
6. **A shape added to a preserved slide discards every edit on that slide** — found in this
   increment, above. Warned, not silent, but all-or-nothing at slide granularity.
7. **Preserved parts are never schema-validated**, by construction ([[70-phase-15-xsd]]). A real
   deck with an invalid layout is preserved faithfully and nothing says so — which is the correct
   behaviour and worth knowing.
8. **`align`'s content-based pairing can guess.** When two or more slides are both edited *and*
   reordered there is nothing left to match on; the writer pairs them with the parts left over, in
   order, and now reports it with `Warning::Degraded` naming each slide and the part it went into
   (`a608c68e`, [[66-phase-15-notes]]). A slide can still take over another's layout, relationships
   and notes page. The real fix is an identity for a slide, which nothing in this chain carries.
9. **An internal hyperlink — one pointing at another slide — is refused** ([[64-phase-15-media]]),
   rather than written pointing at nothing.
10. **The inherited Phase 14 criterion is still open**: `--fidelity agent` was to cost ≤ 15 % of
    `full` and measures ~100 % over the deck corpus, because the two levels differ by one line for
    these decks. It is in the suite as an `#[ignore]`d test rather than softened — closing it changes
    what a fidelity level *means*, which is a specification decision for the owner, not a test to
    relax.
11. **`docx_roundtrip_is_idempotent` fails on `corpus/docx/footnotes.docx`** (`88ff8e11`),
    pre-existing, unrelated to presentations, and **still red at this phase close**. Named here so
    the close does not bury it: 666/1/1 is the honest number, not 667/0/1.
12. **`--fidelity` is `full` throughout both gates** ([[70-phase-15-xsd]]). Whether an `agent` or
    `standard` rendering writes a valid package has never been asked.
13. **No real-world decks, and no `p:oleObj` fixture.** `AGENTS.md` §6 rules real documents out of
    the corpus; the LibreOffice-produced decks of spike P3 are the closest stand-in for a foreign
    producer, and item 7 of the P2 form is the first chance to get PowerPoint's own bytes back
    through the reader.

## What the next phase inherits

Phase 16 is charts, embedded objects and thumbnails. It starts from a writer that already puts a
chart's XML back untouched and a reader that records it with its markup — item 1 of Phase 16 is
turning that opaque part into data, and deck A of the P2 form is the fixture that says whether the
opaque version was ever trusted by PowerPoint in the first place. It should not start before that
form is signed: a chart data model built on top of a package PowerPoint repairs would be built on
sand.
