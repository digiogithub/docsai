# 80 — Phase 16-D: the objects that stay opaque, confirmed end to end

Increment **16-D** of [[75-phase-16-plan]]. The only increment of the phase whose deliverable is
**not a feature**: SmartArt, OLE, transitions and animations have read as a stub plus a sidecar raw
fragment since 13-I ([[43-phase-13-raw]]) and have been written back since 15-D
([[65-phase-15-raw]]), and what had never been asserted anywhere is the *whole loop* on packages
that carry them. The plan's words: «anything that fails here is a defect report, not a redesign.»

> **Numbering.** The plan calls this entry `79`. `79` was taken by 16-H
> ([[79-phase-16-cache]]), which landed first; this is `80` and nothing else moved.

## What was added

- `corpus/pptx/ole-embedded.pptx` — the `p:oleObj` fixture item 13 of [[72-phase-15-close]] names
  as the one the corpus never had, generated by `corpus/generate.py` like every other.
- `crates/docsai-office/tests/pptx_opaque_objects.rs` — eleven assertions over three decks
  (`ole-embedded`, `smartart-fallback`, `raw-preserved`), covering read, write, and the loop
  through DocMark and back.
- One defect fixed in `crates/docsai-office/src/pptx/write_gen.rs`, below.

## The fixture, and why it has two slides

An embedded object reaches a slide two ways and the reader has two branches for them, only one of
which any file in this repository had ever exercised:

- **Slide 1**, the ECMA-376 spelling: a `p:graphicFrame` whose `a:graphicData@uri` ends in `ole`.
  The stub's kind comes from the uri, through `held_kind`
  (`crates/docsai-office/src/pptx/mod.rs:529`).
- **Slide 2**, the spelling PowerPoint actually writes: the same frame inside an
  `mc:AlternateContent`, with a picture in the fallback for a consumer that cannot activate the
  object. The uri is *inside* the `mc:Choice`, so naming the stub from it would call the object
  `other`; `wrapped_kind` (`mod.rs:512`) finds the `p:oleObj` element itself. That function has
  existed since 13-I with no fixture behind it, and its `element.name == "oleObj"` line is the one
  this deck is here to execute.

The two payloads differ on purpose too. The worksheet is a **whole OPC package** reached through a
`package` relationship; the equation is an **OLE2 compound file** reached through an `oleObject`
one. Neither is ever opened by this project, and the tests compare both members' bytes at the end
of the loop rather than merely asserting the object «is there» — the failure spike P3 §2.4
measured was four parts of five silently dropped, with nothing visible to notice it by.

The `.bin` is an OLE2 header and filler, not a real equation, for the reason the macro fixture's
`vbaProject.bin` is not a real macro: a reader that must never look inside the payload gains
nothing from a payload that could actually be activated, and gains a hazard.

Both slides carry a title and four lines of real body text. That is not decoration: a deck whose
only content is an object is not what a deck looks like, and the residue budget of risk P4
(`crates/docsai-convert/tests/plain_residue.rs:401`, 18.0 % corpus-wide) is measured over the
corpus as it stands. It is unmoved and was never a candidate for being moved.

## What is now proved, and where

Each claim is one test, so a failure names which half broke.

1. **The reader tells an agent what it is looking at.** Both objects come back as
   `RawShapeKind::Ole`; the SmartArt stub carries the fallback's own words
   (`Planificar · Ejecutar · Revisar`) rather than swallowing them behind a payload; the transition
   and the timeline come back as two slide-level fragments in the order the part states them.
   Two objects, two fragments, two warnings — and nothing else claimed.
2. **The package is the package that was read**, byte for byte, and the members that carry an
   opaque object are compared individually so a regression says *which* object was lost. The write
   side emits **no warning at all** on these three decks: nothing was lost, so nothing is reported
   as lost, which is the other half of §7 rule 3.
3. **The loop does not lose the object.** `pptx → DocMark → pptx` on an untouched deck gives back
   the package it was given, byte for byte — through a serialiser, a parser, new node ids and
   slides rewritten from the text that survived. With an edit in the DocMark, the retyped title is
   in the package and the object beside it is unchanged.
4. **Rule 8 holds at every level**: the `.ole` stub is in `full`, `agent` and `standard`, and at
   `plain` each object leaves a `dropped:` warning rather than a silence.
5. **A deck written without its preserved package says what it could not write**: one `Degraded`
   per object naming the slide, and the stub's label standing where the object was.

Claim 3 is the one the writer's own tests cannot see. The deck parser leaves `Presentation::raw`
empty, so every stub comes back pointing at a payload nothing carries; the object survives only
because the preserved skeleton holds it, exactly as [[65-phase-15-raw]] decision 4 says.

## The one defect fixed

**A generated deck dropped `p:transition` and `p:timing` in silence.**
`write_gen::slide_xml` walks the shape tree, and slide-level markup hangs off `p:sld` *beside* it —
which is the same blind spot `read_slide` had until 13-I, now on the write side. Reproduction
before the fix: read `corpus/pptx/raw-preserved.pptx`, set `Presentation::skeleton` to `None`,
write. Three `Degraded` warnings came back, all about shapes; the transition and the timeline were
not in the package and not in the report. `write_gen.rs:374` now reports them, and the assertion is
in `a_deck_generated_without_its_package_names_every_object_it_could_not_write`.

The fix is a warning, not a rewrite. Writing a preserved subtree into a generated slide would mean
splicing markup from one package into a part built on a different master and theme, which is 15-G's
design to revisit and not this increment's licence.

## What was refused

- **The stub does not learn `progId`.** An agent reading `::: {.ole}` cannot tell an embedded
  worksheet from an embedded equation, and `progId` is precisely the string that would tell it.
  Carrying it means a new attribute on a stub container, which is normative DocMark
  (`docs/docmark-specification.md` §11.2 rule 8) — a specification change made to improve a
  reading, not to make a test pass, and therefore one that is argued in its own increment or not
  at all. **Refused here, written down as a gap.**
- **The `mc:AlternateContent` stub keeps no name and no geometry.** See the carried defects below.
  Recovering them means descending into a branch, and [[43-phase-13-raw]] decision 6 refuses to
  descend on purpose: «choosing between `mc:Choice` and `mc:Fallback` is the consumer's job». Taking
  only the geometry looks contained until the two branches disagree about it, and then the reader
  has picked one. That is a redesign of a recorded decision, not a bug fix.
- **The residue budget and both gates were left where they are.** Nothing here needed them moved.

## Carried defects, with reproduction

1. **A stub over `mc:AlternateContent` has no name and no position, so it sorts last on its slide.**
   `raw::name_of` and `raw::geometry_of` (`crates/docsai-office/src/pptx/raw.rs:96` and `:112`) look
   at the element's own children, and `mc:AlternateContent` has neither a `cNvPr` nor an `xfrm` —
   they are one level down, inside each branch. Reproduce: `docsai convert
   corpus/pptx/ole-embedded.pptx -o deck.dmk.md` and compare the two stubs — slide 1's carries
   `name="Hoja de cálculo 1" pos="4400000emu,2000000emu"`, slide 2's carries nothing but `.ole` and
   its `raw=` id. `order::sort` reads a shape with no position last, so an object wrapped this way
   is reported at the end of the slide whatever its actual place. Harmless on both current fixtures
   (the object *is* last); wrong on a deck where it is not. Same for `smartart-fallback.pptx`.
2. **A picture inside an opaque object is not an asset of the deck.** `ole-embedded.pptx` carries
   `ppt/media/image1.png` — the snapshot every renderer actually draws in place of an OLE object —
   and `docsai inspect` reports `"pictures": 0` and `"media": []`, because the picture is inside the
   raw fragment and the reader never descends. Reproduce:
   `cargo run -p docsai-cli -- inspect corpus/pptx/ole-embedded.pptx`. The bytes are safe (the part
   is in the skeleton and comes back byte for byte); what is lost is that an agent extracting a
   deck's images gets everything except the one image an OLE object is *seen* as.
3. **DocMark carries nothing at all for a transition or a timeline.** The serialiser warns
   `RawBlockDropped { id: "raw-0003", format: "pml" }` for each, so the loss is announced — but the
   deck parser then leaves `Slide::raw` empty, so a model that went through DocMark can never warn
   about them again, and the fix of this increment cannot fire on that path. This is the sidecar
   gap [[65-phase-15-raw]] decision 4 names, unchanged by 16-D and inherited by whichever increment
   makes the deck writer reference the sidecar.
4. **Neither branch of an `mc:AlternateContent` is validated by `corpus/schema_gate.py`.** The gate
   selects `mc:Fallback` before validating (`schema_gate.py:63`), so slide 2's `mc:Choice` — the
   branch that holds the actual `p:oleObj` — is never checked against the XSD. Slide 1's plain
   `p:graphicFrame` form *is*, and validates, which is the only evidence this repository has that
   the fixture's OLE markup is schema-valid.

## One new dependency, and why it is not one

`docsai-office` gains `docsai-docmark` as a **dev-dependency**. The loop this increment exists to
assert has one end in each crate, and `crates/docsai-convert` — where the equivalent pipeline test
for 15-D lives — was being edited concurrently by another increment and was off limits. It adds no
edge to the shipped graph (`docsai-docmark` depends on `docsai-model` alone, so there is no cycle)
and no third-party code. §7 rule 4 asks for the justification in writing; this is it.
