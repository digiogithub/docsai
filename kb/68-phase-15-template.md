# 68 — Phase 15 G: the deck with no skeleton

Increment **15-G** of [[61-phase-15-plan]], on top of [[67-phase-15-autofit]]. The largest of the
phase, and the one that inverts its own rule: everything from [[62-phase-15-package]] to
[[67-phase-15-autofit]] exists to *preserve* a package and splice into it, and this increment is
about the two decks that have nothing to preserve — Markdown typed by hand, which never had a
package, and a slide the model **added**, which has no part to be spliced into ([[66-phase-15-notes]]
refused both by name and pointed here).

Analysis §6.6, restated: *«an agent writing plain Markdown with no attributes at all must produce a
correct pptx: automatic layout selection from content shape»*. That is what removes the
«generate → fail → fix» cycle, and it is the acceptance criterion this increment owns.

## What changed

- `corpus/generate.py`: `office_default_template()` and `TEMPLATE_PATH`, which write
  `crates/docsai-office/assets/default-template.pptx`; `digest_tree` covers it, so
  `--check` gates it like a corpus file (129 generated files, not 128).
- `crates/docsai-office/src/pptx/write_gen.rs` (**new module**): the layouts of a package as the
  chooser sees them (`layouts_of`), the rules (`choose`), and a `p:sld`, an `a:tbl`, a `p:pic`, a
  text box and a `p:notes` written from the model (`slide_xml`, `notes_xml`).
- `pptx/write.rs`: `TEMPLATE` (`include_bytes!`), `skeleton_bytes` returning it instead of a typed
  error, `seed` and `Seeded`, `NewParts`, `claims` (split out of `align`), `free_part`,
  `canvas_of`, `list_prefix`; `rebuild_slides` takes the generated parts and skips them;
  `content_types` learned to add an `Override` as well as a `Default`.
- `pptx/write_text.rs`: `esc_text` is `pub(super)`; `pptx/mod.rs`: the new module.
- `docsai-convert`: the `SUPPORT` note, and the end-to-end test
  `attribute_free_markdown_becomes_a_deck`.

## The design question, and the answer

**Where does the template come from, and is a generated deck a «skeleton» to the rest of the
writer?** The answer taken is the cheapest honest one: **a template *is* a preserved package**, and
the writer never learns that this deck's package came from `include_bytes!` rather than from the
asset store. `skeleton_bytes` returns one or the other and every mechanism of 15-B..15-F —
the splice, the media re-injection, the `_rels` and content-type edits, the notes rewrite, the
`p:sldIdLst` restatement, the stale-autofit drop — goes on working unchanged over it. There is no
second code path for «generated decks», and no place where the two can drift apart.

What that leaves is one genuinely new operation: **a part the package does not have**. It is done in
a *seeding* pass that runs before the rewriting one and produces the package the rewriting works on:
generate the missing slide parts and notes pages, splice `p:sldIdLst`, the deck's relationships and
`[Content_Types].xml`, and hand the result to `rebuild_slides` as if it had been read from disk. A
deck typed as Markdown is then simply *the template plus N added slides*, which is why the deck with
no skeleton and the slide the model added are one increment and one mechanism rather than two.

The alternatives considered and rejected:

- **Generating a package from the IR.** That is spike P3's `naive` mode, whose measurement is the
  reason the whole phase exists. A theme, a master, four layouts and a notes master written from an
  IR that models none of them is an invention, not a conversion.
- **A second writer for skeleton-less decks.** Two writers that must agree about DrawingML text,
  bullets, hyperlinks and autofit and have no test that they do. The one thing 15-B bought — the
  reader and the writer being exact mirrors — would have been spent immediately.
- **A prototype slide in the template, spliced into.** It fails on the first slide whose shape count
  is not the prototype's: `rewrite_slide` refuses a mismatch and copies, so the caller would get the
  template's own placeholder text. The generated part has to have the model's shapes in it, so it
  may as well be generated whole.

## Where the template comes from

`crates/docsai-office/assets/default-template.pptx`, **9 112 bytes**, generated by
`corpus/generate.py` (`office_default_template`) from XML written in that file, under this
repository's own licence. There is no binary of unknown provenance in the tree, every byte of it is
reviewable as source in a diff, and `python3 corpus/generate.py --check` fails if the file drifts
from the source that states it — the same gate the corpus has had since Phase 0.

It holds a slide master with the two placeholder positions and the text styles, **four layouts**
(«Title Slide» with a centred title and a subtitle, «Title and Content», «Title Only», «Blank»), a
notes master, the theme the master requires, `tableStyles.xml`, the document properties, and a
`p:sldIdLst` that is **present and empty**. A 16:9 canvas (12 192 000 × 6 858 000 EMU), which is
what every version of PowerPoint since 2013 creates by default — the corpus is 4:3 and stays so,
because a fixture measures a reader and a template is what a *new* deck should look like.

Four layouts and not two: the two rules of §6.6 name two of them, and a chooser needs something it
can decide *against*. «Title Only» and «Blank» exist so that a layout with a body is a positive
choice rather than the only one there is.

## The rules, stated

`write_gen::choose`, in order:

| the slide holds | the layout |
| --- | --- |
| a layout the model names, and the package has that part | that one, and no rule is applied |
| one title placeholder and one body placeholder | the plainest layout with a title and a *content* placeholder — «Title and Content» |
| one title placeholder and nothing else | the layout whose title is a **centred** one — «Title Slide» |
| anything else | the title-and-content layout, with a `Warning::Degraded` naming the slide, what it holds and which layout it went on |

Three things about them are deliberate:

1. **A layout is chosen by its placeholders, never by its name.** The same code runs against the
   embedded template, whose layouts are known, and against a user's own deck, whose layouts are
   named in whatever language it was authored in. `«Title and Content»` in the table is a
   description of a shape, not a string being compared.
2. **A subtitle is body-like everywhere else in this crate and must not be here.** `PhType::is_body`
   includes `Subtitle`, so the first version of the chooser picked «Title Slide» for a title with
   bullets under it: its subtitle satisfied «a layout with a body». `LayoutOption::content` is the
   narrower question — a `body` or an `obj` — and it is what tells the two layouts apart. Found by
   reading the written package, not by a test, which is why the smoke test is in the verification.
3. **The slide states the layout's own `p:ph`, not the model's.** A title written against «Title
   Slide» is that layout's `ctrTitle`; writing `title` there leaves the box unmatched and the text
   lands at the master's position instead of the layout's. What binds a slide placeholder to its
   layout is the type and the `idx`, and both come from the layout.

## Non-obvious decisions

1. **Seeding decides the pairing with `align`'s own first two passes.** Which package part a model
   slide *is* has no answer in the file ([[66-phase-15-notes]] decision 1), and now two pieces of
   code need the same answer: seeding, to know which slides have no part, and `align`, to pair them
   afterwards over the seeded package. So the two passes are one function, `claims`, and seeding
   fills the rest exactly as `align`'s order-fill does. The slides that get new parts are the
   *tail* of the unmatched ones, which is what makes a slide inserted in the middle land in the
   middle: the untouched slides around it still match on their signature.
2. **The new `p:sldId` entries are spliced in at the model's position, not appended.** The list
   comes out in the model's order, so `align` on the seeded package matches everything on its first
   pass — the generated part's signature is the model's by construction — and `restate_deck` finds
   nothing left to restate. Appending would have worked too and would have left the second pass
   recovering an order the first pass already knew.
3. **A generated slide is not rewritten.** `Rebuild` carries the set of parts seeding wrote, and
   `rebuild_slides` skips them: the part already says exactly what the model says, and running the
   splice over it would report a chart or a table as «copied from the preserved package», which is
   a warning about a package that never existed. The seeding pass emits its own warnings, once.
4. **An `a:tbl` from the model, on the terms [[64-phase-15-media]] set.** That increment pointed
   here for a table whose grid moved, «because a deck with no skeleton has nothing to preserve and
   must generate one anyway». The writer exists now — grid, rows, `gridSpan`/`rowSpan`/`hMerge`/
   `vMerge`, cell bodies, a style reference — and it is used **only on a slide this writer
   generates**. A table inside a *preserved* slide is still spliced cell by cell and a preserved
   grid the model moved is still copied and named, because regenerating it would throw away the row
   heights, the `a:tcPr` and the band flags the IR does not model — which is 15-C's whole argument
   and is not weakened by there being a writer. `kb/64` is amended to say that rather than to
   promise what this does not deliver.
5. **A notes page for a slide that already has a part, too.** 15-E refused a note typed onto a slide
   with no notes page and pointed here. Doing only the added-slide half would have left a message
   naming an increment that had come and gone, which is the failure [[66-phase-15-notes]]'s last
   bullet names. So seeding also writes a page for an existing slide, splicing the *one* new
   relationship into the `_rels` the slide already had. What is still refused is a notes page in a
   deck with **no notes master**: there is nothing to hang one from, and inventing a notes master is
   inventing a design. The message says that now instead of naming an increment.
6. **A shape that cannot be generated is a text box carrying its label.** A chart's data lives in a
   part of its own, a diagram's in four, an OLE object's in a binary — none of them is in the IR,
   and none can be conjured onto a slide the writer is building from nothing. Emitting the shape
   with a hole in it, or dropping it and leaving the model's shape count disagreeing with the
   part's, are both worse than a visible box saying what the object was. It is warned, by name, per
   shape.
7. **Using the template at all is reported.** A deck that came through DocMark without its
   `skeleton:` file beside it is indistinguishable here from a deck typed by hand — the parser sets
   `skeleton: None` in both cases, having already warned in the first. Rather than guess which
   happened, the warning states the *outcome*: this deck was written on the embedded template, so
   its theme, its master and its layouts are docsai's. That is true either way, and for the deck
   whose skeleton went missing it is a real loss that would otherwise be silent.
8. **A deck with no package and no slides is a typed error, not an empty file.** The template on its
   own is a valid package that is not a deck: `p:sldIdLst` would be empty and PowerPoint does not
   open that. Writing it would answer a caller's mistake with something that looks like success.

## Known losses, written down rather than discovered later

- **A generated deck's design is docsai's.** Fonts, colours, positions and the four layouts come
  from the template; nothing in DocMark states a theme, and `layouts:` in the front matter is a
  catalogue the *reader* wrote, not a design the writer can rebuild. Warned once per deck
  (decision 7).
- **A free shape's position is invented.** A picture, a table or a text box on a generated slide
  states no geometry in plain Markdown, so the writer lays them down the layout's content area,
  sharing it in reading order. That is a choice, not a recovery: two shapes on a slide get half the
  area each, and a picture with no stated size is stretched to its slice rather than drawn at its
  natural size. A model that *does* state a position (a `full` round trip does) keeps it.
- **A picture that already exists in the package is written again.** `Media` deduplicates by asset
  id within one write, but a generated slide reusing a bitmap another slide already carries mints a
  new `ppt/media/imageN.<ext>` rather than reusing the existing part. Costs a duplicated image in a
  deck where a slide was added; loses nothing.
- **`docProps/app.xml` is not updated.** It states slide counts and titles for a deck that has since
  gained slides. PowerPoint recomputes it on save and no reader in this project consults it.
- **A chart, a group, a diagram or an OLE object on a generated slide is a labelled text box**
  (decision 6), and a group's children are lost with it — the group is one shape to the IR
  ([[65-phase-15-raw]]).
- **A slide-level raw fragment cannot be re-injected into a generated slide.** There is no
  `p:transition` or `p:timing` to match against, and the payload is not written: a deck parsed from
  DocMark carries no payloads at all anyway ([[65-phase-15-raw]] decision 4).
- **An internal hyperlink is still refused**, exactly as in 15-C: the IR records neither the action
  nor which slide the target names.
- **The parser still needs `source-format: pptx` in the front matter** to know that a `##` heading
  is a slide. The *body* is attribute-free, which is what §6.6 asks for, but a `.md` file with no
  front matter at all parses as a text document and writing it as a deck is refused by shape.
  Deciding a deck from the conversion *target* is a change to the parser's contract, not to this
  writer, and it was left alone.

## How it was verified

- **Seven new tests in `pptx::write`** (166 in the crate, up from 159; two obsolete refusal tests
  removed): `a_deck_with_no_skeleton_is_written_on_the_embedded_template` (the parts, the layout
  chosen, the `p:ph` the layout declares, the `Override`, the deck relationship, the `p:sldId` that
  names it, and the deck read back), `a_title_only_slide_is_written_on_the_title_layout` — which
  also asserts that a slide the rules answer for is **not** reported, the false-warning trap —
  `content_that_matches_no_rule_is_written_and_named`,
  `a_shape_that_cannot_be_generated_is_named_and_stands_in`,
  `adding_a_slide_writes_the_part_the_package_did_not_have` (and the two slides that were already
  there are byte for byte the parts that were read),
  `a_slide_added_in_the_middle_lands_in_the_middle`,
  `a_note_on_an_added_slide_with_no_notes_master_is_named`,
  `a_note_on_a_slide_with_no_page_gets_one_written`, and
  `a_deck_with_no_skeleton_and_no_slides_is_refused`.
- **The corpus-wide byte-identity tests of 15-A and 15-B are unchanged and green.** They are the
  regression guard for this increment more than for any other: seeding runs on every write, and
  they say it changes nothing when the model matches the package.
- **The end-to-end test the increment owns**, `attribute_free_markdown_becomes_a_deck` in
  `docsai-convert/tests/deck_convert.rs`: Markdown with no attribute in its body converted to
  `.pptx`, then the parts, the content types, the `p:sldIdLst`, both layout choices, and — because
  P3 §2.4 measured LibreOffice accepting five dangling relationships in silence — **every
  relationship of every part resolved against the parts the package actually carries**.
  `deck_convert`: 12 passed, 1 ignored.
- `cargo test --workspace --no-fail-fast`: **655 passing**, only the pre-existing
  `docx_roundtrip_is_idempotent` failing (`corpus/docx/footnotes.docx`, from `88ff8e11`, untouched
  by this increment). `clippy --workspace --all-targets -- -D warnings` clean, `fmt --all` applied,
  `python3 corpus/generate.py --check` clean at 129 files.
- **By hand, outside the suite**, in a scratch directory so nothing was left beside the corpus:
  two decks converted from plain Markdown and unzipped part by part. The first (a title with
  bullets, then a title alone) has `slide1` on `slideLayout2.xml` («Title and Content», `p:ph
  type="title"` + `type="body" idx="1"`) and `slide2` on `slideLayout1.xml` («Title Slide»,
  `ctrTitle`); `[Content_Types].xml` carries both `Override`s;
  `ppt/_rels/presentation.xml.rels` carries both slide relationships and `p:sldIdLst` names them by
  id. The second added a GFM table, an image and a notes blockquote: `ppt/media/image1.png` is the
  file that was on disk, `[Content_Types].xml` gained `<Default Extension="png"/>`,
  `ppt/notesSlides/notesSlide1.xml` holds the note and its `_rels` point at the notes master and at
  the slide, and the slide's own `_rels` hold the layout, the notes page and the image. Both
  packages were converted **back** to DocMark by the reader, which is the only opinion in this
  project about what is in them, and came back as the decks that were typed.
- The **LibreOffice render was not run**: the installation on this machine is broken
  (`soffice.bin: error while loading shared libraries: libreglo.so`), as it was for 15-D, 15-E and
  15-F. That matters more here than anywhere else in the phase, and it is worth saying plainly:
  **no application has opened these packages**. What has been verified is that the archive holds
  the parts an OPC package needs, that every part has a content type, that every relationship
  resolves to a part that exists, that the XML parses, and that this project's own reader recovers
  the deck from it. What has *not* been verified is that PowerPoint opens it without offering to
  repair it — which is the failure mode the whole phase is measured on, is risk **P2**, and is
  15-K's checklist run by a human. The XSD gate of 15-I is the other half of that answer and would
  catch a schema-invalid generated part; it does not exist yet either.
