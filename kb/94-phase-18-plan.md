# 94 — Phase 18 plan: ODP ⇄ DocMark

Implementation plan for **Phase 18** of [`docs/development-plan-v2.md:353`](../docs/development-plan-v2.md),
opened after Phase 17 closed patch editing ([[93-phase-17-close]]).

Objective as the plan states it: **symmetry with `.odt`/`.ods`.** `docsai-odf` reads and writes text
documents and spreadsheets; it does not read a presentation. A `.odp` today is a format this project
refuses. Phase 18 makes the third ODF class a first-class citizen of the same IR, the same DocMark-P
profile and the same skeleton mechanism the pptx path uses.

The plan marks this phase **parallelizable with Phase 19**, and it is: Phase 18 lives in
`crates/docsai-odf`, Phase 19 in the legacy path beside `.doc`.

## What is already decided, and this phase must obey

- **The IR root is not new.** `Document::Presentation` (Phase 13-A) is the root a deck reads into,
  and `docsai-model` gains nothing structural here. If a `.odp` construct does not fit, that is a
  finding to argue, not a licence to add a second presentation model.
- **The DocMark-P profile is not new either.** DocMark 1.2's eight rules ([[47-phase-14-spec-1-2]])
  are what a deck serialises to, whatever package it came from. A `.odp` that needs new syntax is a
  specification change and is argued as one.
- **De-automatization is `docsai-odf`'s existing discipline** ([[07-phase-4-odf]]): ODF's automatic
  styles are resolved into the IR rather than carried, exactly as the `.odt` and `.ods` readers do.
  Read `crates/docsai-odf/src/styles.rs` before inventing anything.
- **The preserved skeleton is the fidelity mechanism** ([[42-phase-13-skeleton]],
  [[62-phase-15-package]]). An untouched `.odp` must come back byte-identical, and the writer
  splices rather than regenerates. ODF is a ZIP package like OPC, but its parts and its
  `META-INF/manifest.xml` are not OPC's — the skeleton's shape for ODF is the first thing to settle.
- **Never degrade silently, never warn falsely** (AGENTS.md §7 rule 3). The cross-conversion task
  makes this the phase's central discipline: pptx → DocMark → odp *will* drop things, and the plan
  says so — «dialect raw blocks dropped with a warning (the documented v1 behaviour)». A drop
  without a warning fails the phase; a warning for something that was not dropped fails it equally.
- **No new crate** (§3), no heavy dependency without written justification (§7.4).

## The question this phase turns on

A pptx slide and a `.odp` `draw:page` are the same idea in two dialects. The IR is the pptx dialect
made general — `Slide`, placeholders, a cascade of layout and master, shapes with EMU geometry. Two
things do not line up, and each increment below must say which side it bends:

- **`presentation:class` versus `p:ph`.** ODF names a frame's role (`title`, `outline`, `subtitle`,
  `notes`) where OOXML names a placeholder type and an index. The mapping is not a bijection.
- **Master pages versus layout + master.** OOXML has two levels above a slide; ODF has one
  (`style:master-page`, with `draw:layer-set`). The cascade in `docsai-model` was built for two.

Neither is settled here. Each is settled in the increment that first needs it, with the argument
written down.

## Increments

Each is independently testable and ends green on `cargo test --workspace`,
`cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`,
`python3 corpus/generate.py --check`, `python3 corpus/schema_gate.py` and
`python3 corpus/render_gate.py --require-renderer`. Each ends in a KB entry and one commit.

### 18-A — the corpus first

The plan's task 3, first, because every later increment is measured against it. `corpus/odp/`
mirroring the traits `corpus/pptx/` carries — one trait per file, generated by `corpus/generate.py`
so `--check` can assert them. The gates learn ODF: `schema_gate.py` has OOXML XSDs and no ODF
relax-ng, and `render_gate.py` renders decks — say what each can and cannot do for a `.odp`, and
close the gap or record it rather than leaving the new format ungated. **The absence of a
spreadsheet gate is already a carried defect from Phase 17; do not add a second ungated format
silently.**

### 18-B — the `.odp` reader

Plan task 1's reading half: `draw:page`, `draw:frame`, `presentation:class`, master pages, with
de-automatization. Settles the two mapping questions above. The `.expected.inspect.json` goldens
land here.

### 18-C — the `.odp` in DocMark

Plan task 2: the same DocMark-P a `.pptx` writes, from a `.odp`. Any construct that does not fit
the eight rules is argued before the specification is touched. `.expected.dmk.md` goldens land here.

### 18-D — the `.odp` skeleton and writer

The package preserved and spliced, with the first acceptance criterion as its test: **odp round-trip
with DocMark identity on the second pass over the odp corpus.** Byte-identity for an untouched
`.odp` is the property to aim at, and if ODF's manifest or its `mimetype` entry make it
unattainable, say exactly why rather than lowering the aim quietly.

### 18-E — the cross conversion

Plan task 3's second half and the second acceptance criterion: **pptx→DocMark→odp and back work for
common traits; drops are warned, never silent.** Every drop is a typed warning naming the construct
and the dialect it belonged to. The test is a matrix over the traits both corpora carry.

### 18-F — the phase closes

Criteria answered with evidence, `docs/`, `CHANGELOG.md`, `AGENTS.md` §1 and `kb/README.md` updated,
and what is carried forward written down rather than discovered later.

## Standing constraints for every increment

- Do not expand scope: increment N does not do N+1's work, and no Phase 19 or 20 work.
- Do not change normative DocMark to make a test pass; argue the change or work within the rules.
- Do not loosen a gate or a metric. The residue budget
  (`crates/docsai-convert/tests/plain_residue.rs:401`, 18.0 % and 15.0 %) is not raisable, and
  `LOOP_MAX_CALLS`/`LOOP_MAX_TOKENS` in `crates/docsai-mcp/tests/wire_cost.rs` are Phase 17's
  acceptance criterion made permanent.
- Every loss is a typed warning; a false warning is the same failure as a missing one.
- English in code, comments, docs and commit messages; Conventional Commits with a crate scope.
- Never run a writing `git` command — this is a colocated jj repository (AGENTS.md §4.1).
- The owner's uncommitted files are never committed, reverted or overwritten:
  `.github/workflows/release.yml`, `.github/workflows/sign-macos.yml`, `dist-workspace.toml`,
  `docs/release-signing.md`.
